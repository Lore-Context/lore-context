Status: Phase 1 draft — private distribution only (design partners + paying customers).

## 1. Executive Summary

Lore v1.3 scores **R@5 96.6%, R@10 98.8%, MRR 91.5%** on the LongMemEval-S
500-question retrieval protocol — the same session-hit metric used in
AgentMemory's public benchmark.

Against the directly comparable AgentMemory hybrid row (BM25 + Vector):
R@5 95.2%, R@10 98.6%, MRR 88.2%. Lore leads on all three headline metrics.

**Important scope boundary**: this is a retrieval-only benchmark. There is no
answer generation and no LLM judge. These scores measure whether the gold
session appears in the top-K retrieved list, not whether the system produces a
correct end-to-end answer.

The numbers reported here are the v1.2 retrieval engine results. v1.3 did not
introduce regression-risk changes to the retrieval path — the v1.3 work
completed stream wiring and the wiki compiler; the hybrid RRF fusion core is
unchanged. A v1.4 incremental appendix (Phase 2, Week 6) will add reranker
on/off re-measurement and end-to-end SLO numbers.

## 2. Methodology

### Dataset and Method

- Dataset: `xiaowu0162/longmemeval-cleaned`, file `longmemeval_s_cleaned.json`.
- Raw set: 500 LongMemEval-S questions.
- Evaluated set: 500 non-abstention questions after excluding abstention types,
  matching AgentMemory's retrieval protocol.
- Indexing: every question builds a fresh session-level index from its haystack
  sessions.
- Metric: `recall_any@K`, MRR, NDCG@10, and local adapter latency.
- Adapter: `scripts/bench-longmemeval-lore.mjs` uses Lore v1.2 `@lore/search`
  weighted RRF fusion with a Postgres-FTS-like lexical stream and a
  pgvector-like offline TF-IDF cosine stream.

The dense stream is an offline deterministic surrogate. It does not call the
production Qwen3 embedding endpoint, does not write to RDS, and does not use
production API keys.

### Scope Note: v1.2 Engine, v1.3 Version

This benchmark run executed against the v1.2 retrieval engine. The v1.3
release completed stream wiring (SQS capture → wiki compiler → pgvector embed
path) and added the BGE cross-encoder reranker behind a feature flag; it did
not change the hybrid RRF fusion logic, the Postgres-FTS lexical stream, or the
pgvector cosine stream. There is no regression-risk path change that would
invalidate the 96.6% number as a v1.3 baseline.

A v1.4 incremental appendix will be published in Week 6, containing:

- v1.4 reranker on/off re-measurement (after Lane C deploys the independent GPU
  instance and promotes reranker to default-on).
- v1.4 P95 / P99 end-to-end latency numbers (Lane 0 baseline + Lane A
  post-optimization).
- Multi-tenant chaos test summary (Lane D, 100 vault × 1000 QPS × 30 min).

### Reproduce

Download the dataset:

```bash
mkdir -p data/bench/longmemeval
python3 - <<'PY'
from huggingface_hub import hf_hub_download
hf_hub_download(
  repo_id='xiaowu0162/longmemeval-cleaned',
  filename='longmemeval_s_cleaned.json',
  repo_type='dataset',
  local_dir='data/bench/longmemeval'

```

Run the benchmark:

```bash
pnpm bench:longmemeval
```

Run ablations:

```bash
pnpm bench:longmemeval:fts
pnpm bench:longmemeval:dense
```

The runner writes local artifacts under `data/bench/longmemeval/`, including
`latest-lore-longmemeval-s-hybrid.json` and
`latest-lore-longmemeval-s-hybrid.md`. These paths are git-ignored.

## 4. Per-Question-Type Recall

The table below breaks down the Lore v1.3 hybrid adapter score by LongMemEval-S
question type.

| Question type | Count | Recall@5 | Recall@10 | MRR | P95 latency |
|---|---:|---:|---:|---:|---:|
| multi-session | 133 | 98.5% | 99.2% | 93.4% | 20 ms |
| temporal-reasoning | 133 | 94.0% | 97.7% | 86.9% | 22 ms |
| knowledge-update | 78 | 98.7% | 100.0% | 98.9% | 20 ms |
| single-session-user | 70 | 97.1% | 98.6% | 93.4% | 19 ms |
| single-session-assistant | 56 | 100.0% | 100.0% | 100.0% | 27 ms |
| single-session-preference | 30 | 86.7% | 96.7% | 64.3% | 20 ms |

The weakest category is **single-session-preference** (R@5 86.7%, MRR 64.3%).
These questions use implicit preference wording — e.g., "what kind of coffee
does the user prefer" inferred from indirect conversational phrasing rather
than an explicit statement. The hybrid lexical + dense fusion retrieves the
right session in 87% of cases at K=5, but the low MRR (64.3%) indicates the
gold session often ranks at position 3-5 rather than position 1. This is the
primary improvement target for the v1.4 reranker evaluation: the cross-encoder
re-scorer should push the gold session higher within the already-correct top-K
set.

## 5. Ablation

The table below uses the internal `v12-core` 23-case gate (not LongMemEval-S).
It shows why hybrid is the only viable production configuration.

| Lore config | Recall@5 | MRR | Stale hit rate | P95 latency | Gate result |
|---|---:|---:|---:|---:|---|
| dense-only | 78.3% | 73.9% | 0.0% | 0 ms | FAIL |
| sparse-only | 78.3% | 78.3% | 0.0% | 1 ms | FAIL |
| postgres-fts-only | 78.3% | 78.3% | 0.0% | 0 ms | FAIL |
| pgvector-only | 78.3% | 73.9% | 0.0% | 0 ms | FAIL |
| graph-only | 30.4% | 30.4% | 0.0% | 0 ms | FAIL |
| `hybrid-v12` | 100.0% | 97.1% | 0.0% | 1 ms | PASS |

Only `hybrid-v12` passes the v1.2 gate. Single-stream baselines fail because
no individual stream covers the full semantic, keyword, temporal, relation,
wiki, and negative test groups simultaneously. This result underpins the
architectural decision to keep all seven streams in the RRF fusion path.

Dataset SHA256: TODO_LANE_E_PHASE2 (will be pinned and published in the Week 6
Phase 2 appendix; the current run uses the HuggingFace canonical download
which has a stable commit hash in the `hf_hub_download` call).

### Important Disclaimers

**Retrieval-only ≠ end-to-end QA accuracy.** This benchmark measures whether
the correct session appears in the top-K retrieved list. It does not measure
whether the system generates a correct answer. A production-equivalent
end-to-end run would need to seed the 500 LongMemEval-S haystacks into an
isolated Lore project, query `/v1/memory/search` with live Qwen3 embeddings
and Postgres pgvector indexing, and evaluate the generated answers against gold
answers using an LLM judge. That run is planned for v1.5+ (see §9 of the
production quality uplift plan).

**Local adapter, not production endpoint.** The benchmark uses a deterministic
offline TF-IDF cosine surrogate for the dense stream. It does not call the
production Qwen3 GPU embedding endpoint. Production latency numbers (P95 ~2
seconds in v1.3, target ≤1 second in v1.4) are reported separately in the SLO
charter.

Week 6 milestones complete:

g4dn.xlarge T4 GPU instance and promotes `LORE_RERANKER_ENABLED=true` to

alongside the retrieval scores as context for enterprise SLA discussions.

isolation guarantees.
