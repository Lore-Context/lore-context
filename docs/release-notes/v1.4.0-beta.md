# Lore Cloud v1.4.0-beta Release Notes

## Summary

Lore Cloud v1.4.0-beta is the Production Quality Uplift Beta for the private
cloud line. Production traffic was cut over to the cache-enabled v14 sidecar
on `2026-05-06T00:21Z` and the release was tagged the same day after the
initial production gate (Redis attach `wired=true`, warm 30-query smoke,
5-minute 50 QPS k6) passed cleanly.

The release goal is pragmatic: keep the real production embedding path, add
Redis-backed embedding cache and request coalescing, and hold the v1.4 phase
target around 1800ms while deferring the stricter 1000ms goal to v1.5. The
24-hour observation window that was originally gating the tag was compressed
into the initial production gate; the v1.3 stack remains preserved on
`127.0.0.1:3000` as the fast rollback target.

## What changed since v1.3.0-beta

- SearchAdapterV14 is active in production with seven diagnostic recall streams.
- Redis ElastiCache-backed embedding cache is wired into the search path with
  LRU fallback and request coalescing.
- Qdrant is running a >=1.10 runtime in production; the post-release audit
  verified Qdrant `1.15.4` and found no native-fusion fallback logs in the
  sampled window.
- Per-stream timeout hardening ships as a v1.4 code default; production has no
  explicit `LORE_STREAM_TIMEOUT_MS` override set.
- Lane B CloudWatch alarms are deployed in AWS with provisional thresholds
  while the baseline JSON remains pending.
- LLM provider fallback chain and authenticated trace / Evidence Ledger routes
  are in the v1.4 line. The bi-temporal production schema and search-audit
  table did not appear in the post-release production schema audit and are now
  v1.4.x patch follow-ups.
- The primary recall-chain inspection route is
  `GET /v1/recall/traces/{trace_id}`; see
  `docs/v1.4-trace-routes-reference.md`.
- PR #30 fixed the Redis attach race by mutating the existing cache instance
  instead of swapping a new instance behind a stale closure.

## Migration notes

- No customer data migration is required for the v1.4 production cutover.
- The v1.3 stack remains preserved on `127.0.0.1:3000` as the fast rollback
  target until v1.4 is tagged.
- Operators must keep Redis ElastiCache reachable from the production EC2
  security group.
- Cache hit rate is expected to improve after normal working-set warm-up; cold
  misses still use the real embedding service.
- Lane B CloudWatch alarms are deployed with provisional thresholds. The
  prerequisite baseline file `data/bench/v13/slo-baseline-2026-05-12.json` is
  still not present on `main`, and SNS delivery subscriptions remain an
  operator follow-up.
- `lore-search-p95` is currently a provisional custom-metric alarm on
  `Lore/SearchV13 SearchP95Ms` at 2000ms because the CloudShell deployment did
  not find a Lore ALB dimension.
- Bi-temporal production columns `t_created` / `t_expired` were not present on
  `memory_items` or `memory_relations` in the post-release audit.
- The `memory_search_audit` table was not visible in the production table
  stats audit.

## Known limitations

- The v1.4 phase SLO target is 1800ms p95 against the production embedding
  path; the stricter 1000ms target is deferred to v1.5 after further cache
  and runtime hardening.
- Production cache numbers cited above were taken from the post-cutover
  initial gate, not the originally planned 24-hour observation window. The
  observation window was compressed in favour of shipping; longer-horizon
  diurnal-cycle and Redis-eviction behaviour remain provisional until Lane B
  alarms are re-locked against a committed baseline and SNS subscriptions are
  attached.
- Reranker GPU work remains follow-up; this release does not claim GPU
  reranker acceleration in production.
- Design partner notification distribution is intentionally manual — see
  `docs/private/design-partner-notification-v1.4.0-beta.md`.

## 2026-05-07 Lane B audit truth-up

A 2026-05-07 production audit found a wider gap between this release-notes
narrative and runtime behaviour than the original "post-release audit" line
implied. The audit landed in the closed operator note
`docs/private/v14-prod-audit-2026-05-07.md`. Headline corrections:

1. Production was running `lore-api-v16:security-fixes` (a locally built image
   from the v1.5/v1.6 line) instead of the GHCR image this document names. The
   image was rolled back to
   `ghcr.io/lore-context/lore-context-api:v1.4.0-beta-cache-fix-main.a825b7d`
   on 2026-05-07; the running SHA `sha256:98622286bbf2da60504aae980b2e94742634b358216c80d9a44f9d60c8efd104`
   now matches the *image identity* line in the `## Production proof` block.
   The behavioural claims in that block (cache hit path active, seven-stream
   RRF firing, k6 50 QPS gate represents production behaviour) remain
   unverified — items 2 and 3 below detail the gaps.
2. The 12 `lore-*` CloudWatch alarms publish to namespaces (`Lore/SearchV13`,
   `Lore/EmbeddingV14`) that received zero datapoints across the audit's 24 h
   window. The v1.4 production container has no `OTEL_*` / `LORE_OTEL_*`
   environment variables, so the alarms are watching empty data and cannot
   fire. The "deployed with provisional thresholds" claim is config-only, not
   behavioural; treat the alarms as non-functional until the v1.5 OTel→CloudWatch
   exporter work lands.
3. AWS/ElastiCache native metrics on `[redacted]embedding-cache` show
   `CacheHits=0`, `CacheMisses=0`, `CmdGet=0`, `CmdSet=0` over the same 24 h
   window. After image rollback the embedding cache reports `wired=true` in
   start-up logs but post-rollback probes still produced `CmdGet=0` and
   `CmdSet=0`, indicating the v14 adapter's embedding-using providers
   (`postgres_pgvector`, `qdrant_dense`, `qdrant_sparse`) are not actually
   firing in production despite `LORE_SEARCH_ADAPTER_V14=1`. Root cause is
   under investigation in v1.5 scope.
4. The five primary SQS queues (capture, embedding, graph, connector, backfill)
   show `NumberOfMessagesReceived=0` across 24 h. Production currently has
   essentially no real user traffic; v1.4 SLO claims that depend on real
   traffic (cache hit rate, p95 latency, reranker behaviour) are unverifiable
   from production data alone until partner notification distribution
   produces real load.
5. SNS topic `lore-ops-alerts` had zero subscriptions before this audit. An
   email subscription to the operator address was created during Lane B
   closure and is awaiting confirmation.
6. EC2 IAM role `LoreContextAlphaEc2Role` was missing `cloudwatch:DescribeAlarms`,
   so the production instance could not validate alarm state. An inline policy
   `LoreLaneBAlarmRead` was added during Lane B closure and verified.
7. A `lore-falkordb` container from the v1.5/v1.6 FalkorDB experiment was
   running on production EC2 sharing the docker network with the v14 API but
   was not invoked by the v14 API path. It was stopped and removed on
   2026-05-07.
8. `LORE_QDRANT_COLLECTION` in production is `lore_memories_v11`, not the
   `lore_memories_v12` value the v1.2 / v1.4 docs describe. Whether v12
   collection bootstrap was deferred is open; v1.5 will reconcile or document.

The takeaway: v1.4.0-beta as published described a more complete production
state than was actually deployed. Lane B closure on 2026-05-07 corrected the
image, attached the SNS subscription (pending confirm), patched the IAM gap,
and removed the orphan container. The remaining unverified claims (cache hit
rate, alarm-driven SLO observation, OTel exporter, search adapter v14
behaviour, bi-temporal schema columns) are deferred to v1.5 with explicit
audit-traceable scope.

## 2026-05-07 metric-name correction (post-PR #55)

The 2026-05-07 v14 production audit reported `CmdGet=0/CmdSet=0` over 24h on ElastiCache cluster `[redacted]embedding-cache`. That metric name does not exist in CloudWatch 's `AWS/ElastiCache` namespace; the correct names are `GetTypeCmds` and `SetTypeCmds`. Re-querying with the correct names showed `GetTypeCmds≈46` over 24h, almost entirely from internal diagnostic probes. Direct in-container Redis verification (`new Redis(LORE_REDIS_URL).set(...).get(...)` round-trip via `docker exec`) returned data correctly and ticked the metric `+1`.

**Conclusion:** cache wiring is functional; the absence of `GetTypeCmds` traffic reflects zero real user search load, not a wiring bug. The original "v14 adapter not actually firing" framing is withdrawn. The Lane A defensive PR (#53) and v1.4 truth-up text remain useful (compose env declaration invariant), but the headline causation is replaced with: "production has zero real user search traffic; cache hit-rate SLO cannot be evaluated yet". The `vaultId=local-dev-vault` artefact in the original 5 internal probes is consistent with curl-localhost-3010 hitting the unauthenticated local-dev fallback (no cloud session cookie), not a production routing bug.
