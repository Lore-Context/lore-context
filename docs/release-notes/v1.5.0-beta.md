# Lore Cloud v1.5.0-beta Release Notes

## Summary

Lore Cloud v1.5.0-beta is the Production Quality Truth-Up + Cleanup Beta for
the private cloud line. v1.5 does not introduce new user-visible features; it
closes the gap between the v1.4.0-beta release narrative and actual production
runtime behaviour, deletes ~3,376 lines of orphan code from main, and lays the
observability infrastructure needed to make the v1.4 SLO claims verifiable.

All six v1.5 lanes merged to main on 2026-05-07. The v1.5.0-beta tag marks the
code-level deliverable. Production image cut and operator activation steps are
separate post-tag actions.

## What changed since v1.4.0-beta

### Lane 0 — main cleanup (PRs #44 + #45, -3,376 lines)

The v1.4 → v1.6 development window landed ~3,382 lines of v1.5/v1.6 orphan
code on main without a corresponding decision record. Lane 0 cleared the debt
in two PRs:

PR #44 (unconditional delete, -1,026 lines) removed eight files with no
external references: the repo-root `src/lib/reranker/reranker-service.ts`
outside the pnpm workspace, the unrouted `cache-middleware.ts`, the archived
FalkorDB Cypher index file, `scripts/deploy-falkordb.sh`, the v1.6 wiki
compiler and routes pair (superseded by the v1.4 `wiki-compiler-v13.ts` that
has tests), the v1.6 schema file that overlapped with an existing v1.3 patch,
and the repo-root `VERSION_PLAN_v1.5.0-beta.md` that duplicated `.omc/plans/`.

PR #45 (decision-group delete, -2,350 lines) deleted five decision-group code
clusters whose user-approved disposition was Delete: the v1.5 cache service
trio (`cache-service`, `cache-keys`, `redis-client` under `apps/api/src/cache/`
— v1.4 `embedding-cache.ts` is the production path), four FalkorDB graph
provider files, `hybrid-orchestrator-v2.ts`, the three `packages/search/src/`
reimplementations, and `v16-feature-flags.ts`. All five groups had zero test
coverage, no entrypoint wiring, and no npm dependency availability in the v1.4
image; any one of them would have crashed the server if accidentally imported.

The v1.4 production code path (`orchestrator-v12`, `search-adapter-v14`,
`embedding-cache`, `redis-client-v14`, `wiki-compiler-v13`) was not touched.
CI stayed green; production `/health` 200 throughout.

### Lane A — compose env fix, PR #53

Root cause of ElastiCache `CmdGet=0` across 24+ hours post-v1.4 release:
`docs/deployment/compose.production.yml`'s `api` service `environment:` block
did not declare the v1.4 cache / v14 adapter env keys. Docker Compose silently
drops host env file values for keys not declared in the service block, so the
`wired=true` startup log seen at v1.4 release came from a manually launched
sidecar container on port 3010, not the compose-managed service on port 3000
that actually serves production traffic.

Fix: 17 env keys (`LORE_SEARCH_ADAPTER_V14`, `LORE_EMBEDDING_CACHE_ENABLED`,
`LORE_REDIS_URL`, and 14 others) are now declared in the `api` service block
with defaults of `0` / empty, making this byte-identical to the v1.3 baseline
when the host env file does not contain the new keys. A new invariant test
suite (`compose-production-env-wiring.test.ts`, 11 assertions) fails the build
if any required v1.4 key is dropped again.

Runtime activation requires a separate operator action — append the activation
values to `/opt/lore/.env.production` and redeploy via `pnpm release:prod`.
The compose patch itself does not change production behaviour. Full root cause
audit in `docs/private/v1.5-f1-v14-adapter-rootcause.md`.

### Lane B — OTel→CloudWatch exporter, PR #48

The 12 `lore-*` CloudWatch alarms deployed during v1.4 were watching
`Lore/SearchV13` and `Lore/EmbeddingV14` namespaces that received zero
datapoints across the audit window because the v1.4 production container had
no `OTEL_*` env variables. Lane B closes this by shipping the full OTel
metrics pipeline.

New file `apps/api/src/observability/metrics-exporter.ts` registers a
`MeterProvider` with six instruments: `lore.search.stream.candidates`,
`lore.search.stream.latency_ms`, `lore.search.stream.timed_out` (per stream),
`lore.embedding.cache.hit_rate`, `lore.embedding.cache.miss_latency_ms`, and
`lore.search.p95_ms`. The entire pipeline is gated by `LORE_OTEL_ENABLED=1`
and is a strict no-op when the flag is unset, so the v1.4 production container
behaviour is unchanged until the flag is set.

The ADOT collector sidecar (`public.ecr.aws/aws-observability/aws-otel-collector`)
is added to `compose.production.yml` on the production network. An
`.env.production-sidecar.example` documents the three new env vars
(`LORE_OTEL_ENABLED`, `OTEL_EXPORTER_OTLP_ENDPOINT`, `LORE_API_IMAGE`).

Production rollout is a separate operator step: set `LORE_OTEL_ENABLED=1`,
add the collector container, redeploy. The Lane D baseline collection scripts
depend on this rollout completing before meaningful metric data is available.

### Lane C — schema wiring, PR #49

The four v1.3/v1.4 schema files were authored during earlier cycles but never
wired into `scripts/apply-postgres-schema.mjs`, leaving production RDS without
the columns and tables the application code expected. Lane C adds them to the
apply targets in correct dependency order:

- `schema-v13-bitemporal.sql` (134 lines): `t_created` and `t_expired`
  TIMESTAMPTZ columns on `memory_items` and `memory_relations` with idempotent
  backfill UPDATE. Required by the v14.1 systemTime filter (PR #31).
- `schema-v14-audit.sql` (27 lines): `memory_search_audit` table for 1%-sampled
  top-K capture. Required by `SearchAuditRecorder` (already exists, not yet
  caller-wired — Lane C-2 follow-up).
- `schema-v14-trace-export.sql` (24 lines): `memory_search_trace_export` for
  design-partner trace inspection.
- `schema-v14-graph-trigram.sql`: trigram index for graph stream lookups.

All four files use `IF NOT EXISTS` / `IF EXISTS` guards for idempotent
re-apply. Production RDS schema was applied 2026-05-07 via SSM.

### Lane D — SLO baseline collection scripts, PR #52

Adds the tooling needed to lock the 12 `lore-*` CloudWatch alarms from
provisional thresholds to evidence-based baselines once Lane B's OTel
exporter is live in production.

`scripts/release/collect-v14-baseline.mjs` pulls 24–72 hour CloudWatch metric
statistics across six metric families (SearchP95Ms p50/p95/p99/mean/stddev,
EmbeddingV14 CacheHitRate, StreamTimeoutRate per seven streams, SQS five
queues, RDS CPU, ElastiCache hits/misses) and writes
`data/bench/v13/slo-baseline-2026-05-12.json`. No new npm dependencies — Node
built-ins plus spawned `aws` CLI.

`scripts/release/relock-v14-alarms.mjs` reads the baseline file and applies
`max(floor, baseline+2σ)` threshold formulas to all 12 alarms via
`aws cloudwatch put-metric-alarm`. Requires explicit `--apply` flag;
`--dry-run` prints the plan without touching AWS.

`docs/v1.5-d-slo-baseline-runbook.md` covers the full operator sequence: Lane
B OTel live → k6 synthetic load (10/100/500 QPS × 1h on staging
`[redacted]`) → collect baseline → relock alarms → verify 12 alarms
exit `INSUFFICIENT_DATA` within 30 minutes.

### Lane E — Qdrant collection truth-up, PR #47

Production `LORE_QDRANT_COLLECTION` was `lore_memories_v11` despite v1.2 and
v1.4 docs both declaring `lore_memories_v12`. Qdrant inspection found:
`lore_memories_v11` had one stale point and an empty payload schema (no tenant
filter pushdown); `lore_memories_v12` had zero points but was properly
bootstrapped with vault_id, project_id, status, memory_type, and
source_provider keyword indices required for tenant filter pushdown.

The env was switched to `lore_memories_v12` on production EC2 and the v14 API
container recreated. `/health` returned 200 with `searchAdapter=v14` and
`embeddingCache=enabled` post-switch. Rollback backup preserved on host as
`.env.production-sidecar.bak-lane-e-2026-05-07`.

### Lane F — secrets migration deferred to v1.6, PR #51

F-7 (migrate seven plaintext credentials from `.env.production-sidecar` to AWS
Secrets Manager) was assessed as too risky to half-ship in the v1.5 window
(estimated 6–10h, touching production container startup). The current state
carries medium security risk: plaintext credentials on EC2 disk, no rotation
audit trail. The risk is documented and accepted for v1.5 scope.

`docs/v1.6-secrets-migration-stub.md` captures the security risk assessment,
full design sketch (seven secret names, IAM policy JSON, entrypoint fallback
flow), ordered implementation plan, and a seven-item acceptance criteria
checklist for v1.6.

## Migration notes

No customer data migration is required for the v1.5 closure. The v1.5 changes
are code-level and deployment-config-only; the running production container
retains v1.4 behaviour until the operator performs the activation steps below.

Operator activation sequence (post v1.5 image cut):

1. Append to `/opt/lore/.env.production`:
   ```
   LORE_SEARCH_ADAPTER_V14=1
   LORE_EMBEDDING_CACHE_ENABLED=1
   LORE_REDIS_URL=redis://[redacted]embedding-cache.nth1h8.0001.apse1.cache.amazonaws.com:6379
   LORE_EMBEDDING_COALESCER_ENABLED=1
   LORE_OTEL_ENABLED=1
   OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318
   LORE_API_IMAGE=<v1.5-image-sha>
   ```
2. Redeploy via `pnpm release:prod -- --sha <v1.5-sha> --yes`.
3. Verify `/health` 200 with `searchAdapter=v14`, `embeddingCache=enabled`.
4. Hit `/v1/memory/search` 5× from a vault-scoped admin key.
5. Within 60s check `aws cloudwatch get-metric-statistics` for `CmdGet > 0`
   on `[redacted]embedding-cache`.
6. Wait 5 minutes; verify `Lore/SearchV13 SearchP95Ms` has at least one
   datapoint in CloudWatch.
7. Run Lane D baseline collection per `docs/v1.5-d-slo-baseline-runbook.md`.

## Known limitations

The v1.5 closure is honest about what is code-merged versus what is
production-active:

- ElastiCache `CmdGet` remains 0 until the operator performs Lane A activation.
  The compose env fix (PR #53) is a necessary but not sufficient condition;
  the operator must also update `/opt/lore/.env.production` with the activation
  values.
- OTel exporter is merged but not live in production. The 12 `lore-*`
  CloudWatch alarms remain in `INSUFFICIENT_DATA` until the exporter is
  running and emitting metrics.
- Lane D baseline collection has not run. The alarm thresholds remain
  provisional (set during v1.4 Lane B CloudShell deployment) until a
  meaningful baseline window is collected after OTel rollout.
- `SearchAuditRecorder` (Lane C-2) is not yet wired into the `/v1/memory/search`
  handler. The `memory_search_audit` table exists in production RDS but receives
  no rows until a follow-up PR wires the caller invocation.
- Production has essentially zero real user traffic (five primary SQS queues
  show `NumberOfMessagesReceived=0` across 24h). SLO claims based on real-load
  behaviour remain unverifiable until partner notification distribution produces
  real traffic. Lane D's baseline collection plan uses k6 synthetic load as an
  interim substitute.
- Secrets migration (F-7) is deferred to v1.6. Seven credentials remain
  plaintext on EC2 disk. Risk is medium severity and documented in
  `docs/v1.6-secrets-migration-stub.md`.

## 2026-05-07 metric-name correction (post-PR #55)

The 2026-05-07 v14 production audit reported `CmdGet=0/CmdSet=0` over 24h on ElastiCache cluster `[redacted]embedding-cache`. That metric name does not exist in CloudWatch 's `AWS/ElastiCache` namespace; the correct names are `GetTypeCmds` and `SetTypeCmds`. Re-querying with the correct names showed `GetTypeCmds≈46` over 24h, almost entirely from internal diagnostic probes. Direct in-container Redis verification (`new Redis(LORE_REDIS_URL).set(...).get(...)` round-trip via `docker exec`) returned data correctly and ticked the metric `+1`.

**Conclusion:** cache wiring is functional; the absence of `GetTypeCmds` traffic reflects zero real user search load, not a wiring bug. The original "v14 adapter not actually firing" framing is withdrawn. The Lane A defensive PR (#53) and v1.4 truth-up text remain useful (compose env declaration invariant), but the headline causation is replaced with: "production has zero real user search traffic; cache hit-rate SLO cannot be evaluated yet". The `vaultId=local-dev-vault` artefact in the original 5 internal probes is consistent with curl-localhost-3010 hitting the unauthenticated local-dev fallback (no cloud session cookie), not a production routing bug.
